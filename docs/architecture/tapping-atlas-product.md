# Tapping Atlas Product (T4)

Date: 2026-08-15

## Pipeline position

```
KNOWLEDGE (T1/T2.x) → RELATIONSHIPS → T3 PROJECTION → T4 TAPPING ATLAS
```

`scripts/generators/generate-tapping-atlas.js` reads **only** `data/projections/tapping/tapping-profiles.json` and `data/projections/tapping/tap-types.json` — the corrected T3 projection (commit `17aab28`). It never reads `data/entities/`, `data/standards/`, `data/datasets/`, or `data/relationships/` directly. If the projection is ever wrong, T4 is wrong in exactly the same way and by exactly the same amount — there is one place to fix it, not two.

## Why field-level and record-level status are shown separately

Every card on the Atlas shows two distinct lines:

- **"Tap drill: Verified / Source-bound"** — reflects `row.tap_drill.status`, specifically whether *this value* was independently cross-checked against a primary standard table.
- **"Overall profile status: Source-bound"** — reflects `row.data_quality.record_status`, which is `source_bound` on all 29 rows today because thread-engagement and tapping-process-parameter data remain unavailable knowledge-layer-wide.

These are deliberately never collapsed into one badge. A card can legitimately show "Tap drill: Verified" and "Overall profile status: Source-bound" simultaneously (true for 9 of the 29 cards) — that combination is not a contradiction, it's the honest state of the data, and collapsing it into a single "Verified" badge would overclaim.

## US customary vs. ISO 2306 — never merged

`tap_drill` (primary) and `alternative_drill` (ISO 2306, UNC/UNF only) render as visually separate blocks with an explicit note ("It is shown separately from BoltLab's primary US-customary drill value and does not replace it") repeated on every card that has one. `alternative_drill` is `null` on all 14 metric rows — not omitted, not hidden, structurally absent because the projection correctly treats ISO 2306 as *the* metric convention rather than a second option.

## Engagement: capability, not recommendation

The Atlas's "Thread engagement" section uses one fixed sentence, not a per-record calculation: BoltLab can compute radial engagement from geometry, but asserts no target percentage, and axial engagement remains `not_calculable`. No numeric engagement value — target or otherwise — appears anywhere in the generated HTML or CSV. `scripts/validators/validate-tapping-atlas.js` greps the entire generated output for 70%/75%/77% and diameter-multiplier patterns and fails the build if any appear.

## Tap-type evidence, not flattened

The tap-type reference section keeps T2.2's four-way classification intact as three separate lists per tap type (manufacturing characteristics, typical applications, manufacturer-specific recommendations), each fact individually tagged verified/source-bound. Nothing is merged into a single descriptive paragraph.

## CSV: same projection, same values, no second source

`downloads/tapping-atlas.csv` is generated by the same script, from the same in-memory projection object, in the same run, as the HTML. `validate-tapping-atlas.js`'s "CSV Matches Projection" and "HTML Cards Match Projection" checks mechanically confirm all three surfaces (projection, HTML, CSV) contain the exact same 29 designations — not just the same count.

## Determinism

The generator has no `new Date()`, no random ordering, and no external I/O beyond reading the two projection files and writing two output files. Run three times against the corrected projection in this phase; all three runs produced identical SHA-256 checksums for both `reference/tapping-atlas.html` and `downloads/tapping-atlas.csv`.

## The lesson this phase encodes permanently

T3 shipped a real bug (`audit/t3-correction.md`) because its own audit narrative was written to describe the *intended* design and never mechanically cross-checked against the artifact it described. T4's validator (`validate-tapping-atlas.js`) is built specifically to not repeat that mistake: every expected count it checks against (verified/source-bound splits, ISO-alternative counts, per-system counts) is *derived from the projection at validation time*, not copied from a report or hard-coded from memory. If the projection ever changes, the validator's expectations move with it automatically.

## What T4 deliberately does not do

- Does not calculate or display a minimum axial engagement length.
- Does not promote any `source_bound` value to `verified`.
- Does not build a calculator, downloadable engagement tool, or API endpoint (a separate future product decision).
- Does not modify the underlying tapping knowledge or projection data — T4 is presentation and product logic only.

## Future consumers

`reference/tapping-atlas.html` and `downloads/tapping-atlas.csv` are the first two consumers of the T3 projection. Both were built to be regenerable from the projection alone, so a future API endpoint or interactive calculator (not built in this phase) could become a third consumer without requiring another knowledge-layer or projection-layer change.
